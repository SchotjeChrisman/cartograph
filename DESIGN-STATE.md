## Answers log
1. Runtime shape: one-shot CLI (each command opens the SQLite file, works, exits). `cartograph mcp` is a thin stdio process over the same file. No daemon. A foreground `cartograph watch` (re-runs incremental index on file events) comes as a later milestone.
2. Workspace: Cargo workspace by feature. Crates: graph (types + SQLite store), index (walker + parsing), languages (one module per language and framework plugin), cluster, query, describe (backends), map (HTML generation), cli (binary + MCP). Dependencies point one way: cli -> query/describe/map/cluster/index -> graph.
3. Store: one graph per directory. The developer picks the root: run in a monorepo root for one graph, or in each repo for separate graphs. Graph lives in `.cartograph/` inside that root. No central database.
3b. Nesting: everything below the root is one graph. Each file gets a repo tag from its nearest .git. A nested `.cartograph/` is skipped (like node_modules) and reported.
4. Scale: designed from the start for the biggest projects, and scalable even beyond that. Implies streaming parse and write, bounded memory, indexed edge tables, clustering that does not need the whole graph in memory. No "small project" shortcuts in core design.
4b. Yardstick: Gecko (mozilla-central) is the real-world scale corpus, chosen over the Linux kernel; Chromium is similar in size and could be a second corpus later. Size from memory only (tens of millions of LOC, several hundred thousand files, C++/Rust/JS/Python): verify exact file and LOC counts when setting up the corpus, then fix numeric budgets (full index time, incremental time, query latency, peak memory).
5a. Output: agents first. Default is dense token-cheap plain text, one line per node/edge with file:line. `--json` returns the full structured result. MCP tools return the same structure. Humans mostly use the map.
5b. Bounding: every query takes `--budget` (default about 2k tokens). Results ranked (nearest, most-connected, same-component first), cut at the budget, ending with a footer: how many more exist and the exact follow-up command to expand (`--component`, `--depth`, `--after <cursor>`).
5c. Name lookup: fuzzy match (FTS5) returns a ranked candidate list when ambiguous (qualified name, file:line, component, edge count), each with a short stable id usable in the next call (`callers @a3f9`). Unambiguous names, qualified names (`nsFoo::Init`) and `file:line` resolve directly. Design note: stable ids must survive re-indexing, so derive them from a hash of qualified name + file path + kind, not from row numbers.
5d. MCP surface: six task-shaped tools, each taking `budget`: `overview` (components and entry points), `find` (resolve a name or question to candidates), `explore` (neighbourhood of a node: callers, callees, contains, with depth), `path` (A to B), `impact` (what breaks if this changes), `coverage` (what was and was not parsed). CLI mirrors them one-to-one, with convenience aliases such as `callers` and `callees`.
6. Components: hierarchical tree (system > subsystem > component > file) from Leiden at several resolutions, seeded and biased by directory structure so names match developer expectations. Ids match across runs by member overlap so descriptions survive edits.
7a. Describe timing: lazy, top-down, on demand. `cartograph describe` fills the top levels first; deeper components only when requested, then cached by component hash. A parent's prompt contains its children's descriptions so cost stays bounded. `--depth N` or `--all` forces a full pass. Index and map work with zero model calls: components then show a generated name and top symbols. Open tension: "on demand from the map" requires a served map or a CLI/agent trigger (see topic 8).
8a. Map delivery: `cartograph map` is a foreground command running a local HTTP server (bind 0.0.0.0, port chosen, offline, no external assets). It streams only the visible level from SQLite as the user zooms and can trigger `describe` for an opened component. The server lives only while the command runs. Supersedes the "static index.html" line in PLAN.md (PLAN.md needs updating when the design pass ends). Static export is not planned.
8b. Map visual: boxes and arrows, one level at a time. Screen shows the children of one node as named boxes with the description beneath; arrows for the strongest dependencies (thickness = edge count). Click drills in, breadcrumb goes up, side panel shows description, key symbols and the equivalent `cartograph` command. Never more than about 50 boxes on screen. Frontend technology (plain JS vs a framework, layout library) not yet decided and needs the user's approval for any dependency.
9a. Plugins: each language = tree-sitter grammar + `.scm` queries file (symbols, calls, imports) + optional small Rust module for resolution rules. Frameworks (WordPress hooks, Laravel routes) have the same shape, layered on a language. All compiled into the binary, selected by file extension, extra grammars behind Cargo features. Adding a language needs a rebuild. No WASM or runtime plugins.
9b. First languages: C/C++, Rust, JavaScript/TypeScript, PHP with Laravel as the first framework plugin (Mainstay is the target). Python is not in the first set (Gecko's Python build scripts stay unparsed and show up in `coverage`). WordPress hooks are no longer first; PLAN.md's language and framework lines and milestones need updating. C++ without compile_commands.json resolves calls by name and scope heuristics only, tagged inferred; whether to read compile_commands.json for include paths and defines is an open design question.
10a. Freshness: files keyed by content hash. `index` re-parses only changed files (git diff plus mtime check for dirty trees) and rewrites only their nodes and edges. Every query first runs a cheap staleness check; few changed files are re-indexed inline, many changed files give a one-line warning with the graph's age. `watch` later repeats this on file events. Branch switches use the same hash comparison. Clusters and descriptions of affected components are marked stale, not recomputed inline.
11a. Agent integration: `cartograph install` registers the MCP server and adds a small skill/CLAUDE.md snippet saying when to call `overview`, `find`, `explore` first. Optional opt-in strict hook (PreToolUse, like Graphify's `--strict`) denies Read/Grep until a graph query has oriented the agent in the session; off by default. Works for Claude Code, Codex and any MCP client. The strict hook needs a coverage escape: if `coverage` says the relevant files are unparsed, the hook must allow Read/Grep.
12a. Distribution: Nix flake (`nix build`) plus GitHub Actions release binaries (static Linux x86_64 and aarch64, macOS) per tag. Tests: per-language golden-graph fixtures, incremental-equals-full-index, fake describer backend, headless-browser check of the map, and a benchmark script against Gecko recording index time, memory and query latency.
13a. C/C++: heuristics by default (resolve `#include` by searching the tree; resolve calls by name plus enclosing namespace/class and imports; tag `inferred`; keep ambiguous calls as unresolved). If `compile_commands.json` exists, use its include paths and defines for exact include resolution and overload sets. No libclang, no compiler dependency.
14a. Requirement: the graph must serve dozens of simultaneous agents plus any user map views. Consequences to settle: (a) concurrent readers must never block on a writer; (b) only one indexer at a time, others must read the last committed snapshot and not queue behind it; (c) concurrent `describe` requests for the same component must be deduplicated; (d) memory per agent process must stay small (no per-process copy of a large in-memory graph); (e) auto re-index on query (10a) must not cause a stampede when 30 agents notice the same stale files.
14b. Concurrency design: SQLite in WAL mode, many processes. Readers never block on the writer. A lock file makes one process the indexer; the others serve from the last committed snapshot and report "indexing in progress". A `jobs` table with claim rows deduplicates index and describe work (also covers the auto-reindex stampede from 10a: only the claim holder re-indexes). Per-process memory stays small: SQLite pages share the OS cache, deep traversals build only a small CSR slice per query. Decision 1 (no daemon) stands. Every query goes behind a small trait so a shared server can be added later if a benchmark (30 concurrent agents on Gecko) shows the file approach is not enough.
15a. Describer input: the component's members (top symbols by connectivity, with signatures and doc comments), its strongest edges to other components, entry points, and its children's existing descriptions. Capped at a fixed token size per call (default about 6k). No file bodies. Output is a name, one paragraph and tags, validated as JSON before storage. Human overrides in `.cartograph/overrides.toml` always win and survive regeneration.
17a. Skip rules: the walk respects .gitignore. Paths matching vendor patterns (third_party/, vendor/, node_modules/, *.min.js, generated-file headers) are indexed but tagged `vendored` or `generated`, de-ranked in queries and excluded from components by default (`--include-vendored` to include). Secret files (.env, *.pem, key files, credential patterns) are never parsed or stored; `coverage` lists what was skipped and why. Patterns overridable in `.cartograph/config.toml`.
